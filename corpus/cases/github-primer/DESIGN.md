# GitHub Primer

## Visual thesis

Primer shows how a technical product can remain dense without becoming visually chaotic. The system relies on stable foundations, compact components, explicit status, responsive behavior, and repeated patterns that expert users can learn once and reuse.

## Signature relationships

- **Density through structure.** Compact UI works because alignment, hierarchy, and state are disciplined.
- **Foundations feed product patterns.** Color, type, layout, iconography, and responsiveness are shared inputs.
- **Repeated jobs deserve repeated solutions.** Similar interactions should not become visually unrelated local inventions.
- **Semantic status matters.** Technical workflows need clear selected, success, warning, danger, disabled, and muted states.
- **Responsive does not mean simplified beyond usefulness.** Important technical context should reflow intelligently rather than disappear by default.

## Layout and density

Favor efficient grids, compact rows, aligned metadata, and clear grouping. Use whitespace to separate conceptual regions, not to make an expert tool artificially airy. Collapse secondary information only when priority is understood.

## Typography

Use compact readable body and control text with clear hierarchy for page titles, section headings, code, labels, and metadata. Monospace should be reserved for code and technical identifiers rather than used as a generic developer aesthetic.

## Color and surfaces

Keep canvas and surfaces restrained so status and interaction colors remain legible. Dark mode should preserve role hierarchy and contrast rather than merely reverse values.

## Components and interaction

Tables, lists, navigation, filters, menus, code-related controls, dialogs, and status indicators should reuse stable patterns. Keyboard and focus behavior are especially important in high-frequency expert workflows.

## Adaptation rules

- Preserve compact clarity, semantic state, reliable repeated patterns, and responsive technical context.
- Change brand palette and typeface only while retaining comparable technical legibility.
- Use developer-specific visual cues only when they correspond to real code or workflow content.

## Failure modes

- Making every surface dark because the product is for developers.
- Using monospace everywhere to signal technical credibility.
- Compressing spacing without improving alignment or hierarchy.
- Hiding critical metadata on mobile instead of prioritizing and reflowing it.

## Evidence boundary

This case is original analysis of public Primer documentation. It does not include GitHub screenshots, logos, or copied product interface assets.
