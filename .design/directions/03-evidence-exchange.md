# Direction 3: Evidence Exchange

## Decision layer

### Thesis

Treat every case as an evidence-bounded, well-explained data package with visible provenance, limits, formats, and recovery paths.

### Why it fits

This direction makes the download itself the main product. Every case explains what the data means, where it came from, what is observed or inferred, what each file contains, and what its limits are before the user downloads it.

It is the strongest option when portable evidence, matching meaning across readable and structured outputs, and dependable download behavior should define the Site.

### Signature traits

- A visible package contract before download.
- Human explanation paired with exact technical metadata.
- Evidence quality and limitations treated as primary content.
- Specific recovery paths for unavailable or failed downloads.
- Readable and structured formats presented as equivalent projections.

### Primary foundation

IBM Carbon owns the grid, semantic layers, component-state logic, and productive versus expressive split.

### Adaptation axis

Download-led evidence delivery.

### Supporting references

- Vercel Geist contributes technical typography roles only.
- GOV.UK contributes exact error and recovery behavior only.
- GitHub Primer contributes complete mobile reflow only.

### Clear risk

The Site can feel like a file registry if package detail overwhelms discovery and visual case character.

## Expert layer

### Composition and hierarchy

A package header leads into context and value, evidence and provenance, readable and JSON format details, limitations, and final download actions. The decision order is clear: understand, verify, choose, then download.

### Typography and density

Human explanation leads. Compact labels, tabular values, file metadata, evidence IDs, and code identifiers occupy separate technical registers. Context and limitations use readable measure, while manifests and provenance use compact rows.

### Color and surfaces

Original semantic roles identify ready, incomplete, unavailable, stale, warning, error, focus, and primary download states. Evidence, manifest, limitations, and action bands use role-based contrast and borders instead of floating cards.

### Interaction and motion

Users inspect contents, switch between readable and structured views, verify limitations, download, and recover from specific failures without losing context. Motion confirms state change but never replaces status text.

### Feasibility

This fits the current static Site. Deterministic readable and JSON projections, privacy filtering, validation, and browser download states are substantial work, but they require no backend.

### Forbidden drift

- No download presented before its context, contents, evidence boundary, and limitations.
- No technical metadata made visually equal to the human explanation.
- No fabricated previews, copied source assets, or decorative code used as proof.
- No generic failure message without the exact problem and next action.
- No Carbon geometry, IBM blue, Geist monochrome identity, or GOV.UK styling.

## Evidence layer

The Carbon basis is supported by `CARBON-E01`, `CARBON-E02`, `CARBON-E03`, and `CARBON-E05`. Geist's narrow typography role is supported by `GEIST-E03` and `GEIST-E05`. GOV.UK's recovery role is supported by `GOVUK-E04` and `GOVUK-E05`. Primer's mobile role is supported by `PRIMER-E02` and `PRIMER-E05`.

The research does not prove the proposed downloads, parity checks, privacy filtering, recovery flows, or mobile behavior. These remain project requirements to implement and verify after direction approval.
